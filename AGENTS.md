# AGENTS.md — working on Cruce

Cruce is **Git coordination for parallel agentic development**: the durable coordination plane for Git work produced by many independent humans and agents, organized as **Namespace → Repository → Workspace**. *Cruce coordinates durable concurrent Git work; other systems execute the work.* The working name should remain easy to change.

Read these before changing domain behavior: [product](docs/product.md) (thesis, boundaries, non-goals), [domain model](docs/domain-model.md) (concepts, lifecycle, authority), [principles](docs/principles.md) (normative rules), [architecture](docs/architecture.md) (current implementation and audit), [decision records](docs/decisions/README.md) and the [contributor guide](CONTRIBUTING.md). [MCP participation](docs/mcp.md) describes the tool boundary. The [roadmap](ROADMAP.md) holds candidates, not work instructions. [Verification](docs/local-verification.md) records evidence and the [changelog](CHANGELOG.md) summarizes user-facing changes. Git history preserves implementation history; do not keep a progress log.

## Boundary

- Apply the boundary test to every capability: if local Git worktrees plus an agent orchestrator would provide essentially the same thing, it does not belong in Cruce. Cruce features rely on durable workspace identity, baselines, provenance, concurrency visibility, reconciliation, exact-revision review, approval, promotion or history across sessions, machines, tools and developers.
- Cruce is not an agent runtime, scheduler, conversation manager, messaging bus, IDE, Git or forge replacement, CI/CD system, cloud development environment or agent vendor platform. Never launch, pause, resume, message or schedule agents, and never store prompts or conversations. Builds, deployments, environments and runtime operations stay external.
- Git stays Git. Use clone, fetch, pull, push, commit, refs and merge as they are. Publication adds retention and review to exact pushed revisions, not transport. Never rewrite existing remotes or upload history silently.
- Stay agent-neutral. Client labels are provenance data; they confer no identity or authority. Client-specific setup is a convenience outside the domain.
- Prefer boring, trustworthy primitives (revisions, baselines, refs, forks, paths, diffs, provenance, approval state) over premature intelligence. Overlap is advisory, never a conflict verdict or scheduling clearance.

## Domain rules

- Stable internal IDs determine identity and storage. Handles, names, paths and remote URLs are addresses. Remote URL matching never proves identity.
- A namespace owns repositories, membership, teams and resource policy. Installation storage is configured once through cf. Personal namespaces have one owner; shared namespaces have Owner, Maintainer, Developer and Viewer. Repository grants are Read, Write and Maintain, capped by namespace role.
- Every repository has a canonical Git repository in Cloudflare Artifacts. A forge may remain upstream; never create a second canonical authority or silent sync.
- A **workspace** is the durable unit of concurrent Git work. It belongs to one repository and one **owner** (a user), has an immutable baseline, and owns one reusable direct fork. It is not an agent session, a process, a checkout or a machine. Its **execution attachment** (worktree, isolated clone or existing checkout) is local, there is at most one at a time, it is explicitly detachable, and it is replaceable by any of the owner's authorized connections. Reports name the attached execution.
- Enforce persistent local writer locks and server checkout reservations. Thirty-second heartbeats; presence shows disconnected after ninety seconds. Elapsed time never releases ownership, detaches or cleans up.
- Agent identity comes from its user and OAuth connection. Effective authority is the intersection of current membership, repository grants, the connection's repository approval (all accessible repositories or a chosen list) and scopes, rechecked on every request and retry. Local setup is once per machine ([ADR 0011](docs/decisions/0011-account-level-connections-and-local-setup.md)).
- Review, evidence, approval and promotion each name one exact revision. Canonical promotion requires authenticated human approval, controller readiness and a non-forced Git update validated against the approved base. Continuing writers reconcile explicitly with Git, verify and obtain fresh review. Fetching or acknowledging proves nothing.
- Keep reported heads, observed fork refs, published revisions and accepted canonical revisions distinct. Publication proves retention, not correctness. Events and observations never approve or promote.
- Namespace resource reservations are atomic across repositories. Retries reuse operation identity and reservation, and uncertain outcomes stay reserved until reconciled. The deployment Artifacts binding is explicit storage authority, never a credential fallback; recorded storage identity cannot be changed implicitly. Repository policy only narrows namespace policy.
- Credentials stay sealed server-side. Git uses 60-second tokens revoked after use. Never expose credentials in source, remotes, configuration, logs or frontend responses. Retain source referenced by published revisions; cleanup is explicit and conservative. Only authenticated console namespace Owner retirement, confirmed by the exact repository name, permits permanent repository deletion ([ADR 0010](docs/decisions/0010-repository-archive-and-permanent-deletion.md)); archive preserves history. Deleting a shared namespace, confirmed by its exact handle, deletes each repository through that same path ([ADR 0012](docs/decisions/0012-namespace-permanent-deletion.md)).

## Implementation

- Keep `src/core` pure and deterministic with injected time and IDs, and add controller tests. The UI renders controller-derived permissions and readiness.
- `src/shared/tools.ts` is the single MCP catalog. Coordination reads must not mutate, initialize storage, provision or call the source provider, including after a cold start. Identity initialization belongs to explicit sign-in; repository initialization belongs to explicit setup or setup retry. Every resource operation declares scope and cost and passes the namespace gate before infrastructure calls.
- Directory DO: identity and address lookup. Namespace DO: membership and atomic reservations. Repository DO (Control Tower): workspaces, changes, artifacts and Git.
- Console: Home lists repositories by what needs attention. Repository tabs are Workspaces, History and Settings, under an attention bar. Workspaces lists each workspace once with its open changes nested under it; there is no separate Changes list. A change opens as a review checklist from controller readiness ending in Promote. Published revisions and evidence live in History. Use plain operational language, never taglines. Scoped header dropdowns switch namespace/repository, and the brand returns to unscoped Home. Repository search is typed in the header with anchored results, and Command/Ctrl K focuses it. Members and Teams exist only in shared namespaces. The avatar identity menu is separate from settings. Preserve keyboard navigation, deep links, Back, retries and late-response protection.
- Offer Create repository, Clone and Attach local checkout. Disclose cloud setup and cost where resources are consumed. No coding chat, editor, agent runtime or intake forms.
- Read the current [Artifacts](https://developers.cloudflare.com/artifacts/llms.txt) and [cf](https://developers.cloudflare.com/cf/llms.txt) documentation before platform changes. Use `cf` and `cloudflare.config.ts`; never use wrangler project commands.
- Cruce is early: remove contradicting concepts instead of adding compatibility layers. Do not reintroduce Flight/radar routes, project/mission aliases, migration adapters, shared-branch execution workspaces, observer workspaces, ref-claim stores, agent pause/resume or sequencing, mandatory scheduling, a workflow engine or a daily operation budget. Other forge, CI/CD, deployment, runtime or workflow integrations need an explicit decision record before becoming core dependencies.

## Layout and verification

`src/core`: ownership, repository decisions, capabilities. `src/worker`: authentication, directory/namespace/repository Durable Objects, Git transport and source retention. `src/shared`: contracts and catalog. `runner`: local bridge, isolation and continuation. `src/ui`: console. `test/browser`: explicitly isolated fixed-clock console fixture.

Preserve pre-existing working changes. `demo/auth-service` and `demo/scenario` are reusable source fixtures; do not reformat them. Historic overlay directory names are fixture paths, not domain entities. Keep demo commit IDs reproducible.

Before committing, run `pnpm typecheck && pnpm lint && pnpm test`, `pnpm test:browser`, `pnpm verify:scenario` and `pnpm exec cf build --mode offline`. Validate hosted publication/promotion in the configured test environment before describing them as live-verified. Update `CHANGELOG.md` for user-facing changes and `docs/local-verification.md` when verification status changes. Record checks and limitations in the review description.
