# MCP participation

[Documentation map](README.md) · [Git and bridge setup](native-setup.md) · [Domain model](domain-model.md) · [Principles](principles.md)

Cruce's MCP interface exposes the Cruce coordination model: repositories, workspaces, baselines, revisions, overlap, divergence, proposals, promotion state and provenance. It is not Git transport, not an agent runtime and not a messaging channel between agents. It does not duplicate generic Git, forge, Cloudflare or agent-framework functionality because that would be easy to expose.

Any MCP client can use it: Claude Code, Codex, Cursor, another agent, an orchestration framework, a relay or a script. Cruce treats them identically. The client name is a label recorded as provenance, never an identity or an authority.

The single executable catalog is [src/shared/tools.ts](../src/shared/tools.ts). Its descriptions, scopes, mutation flags, resource classes and input fields drive both the hosted server and the local bridge. Entries marked `bridgeOnly` are local computations; hosted discovery and dispatch exclude them. Shared schemas live in [src/shared/platform.ts](../src/shared/platform.ts). Consult those files for exact arguments rather than a copy here.

## Connection paths

| Path | What it does | Client responsibilities |
| --- | --- | --- |
| Local stdio bridge: `cruce mcp --server URL --client NAME [--cwd /absolute/path/to/checkout]` | Connects to hosted `/mcp` with the tool's account-level OAuth connection. Binds to the checkout the tool works in, creates isolated worktrees, attaches them and reports local Git state | Start in a Cruce checkout; work in the returned directory |
| Direct hosted MCP: `https://YOUR_HOST/mcp` | Coordination through OAuth for the repositories the connection approves | Provide local isolation, locks, attachment, heartbeats and change reports yourself, naming the attached execution on every report |
| Git smart HTTP | Normal clone/fetch/pull/push with the Cruce credential helper | Use Git, not MCP, to move source |

The bridge supplies namespace, repository and execution identities, plus mutation idempotency keys, from local connection state. Workspace and change tools accept an explicit `workspaceId` for bridge state selection (artifact/proposal IDs still identify the exact reviewed record); omitting it uses the bridge's current workspace. A single bridge can start and address several workspaces in independent worktrees without detaching the others. Local state and uncertain mutation identities are stored separately for each workspace, with a repository-local lookup shared by CLI and MCP processes. Each operation reloads its selected state, so CLI continuation and publication are visible without reconnecting MCP. Local lookup selects work, never authority: requests use the current connection's credentials and the server rechecks ownership and scopes. It handles `start_workspace` by creating and attaching a dedicated worktree for agent writers. A direct remote call only registers the workspace; it creates no local files and launches nothing.

The bridge binds to a checkout from local state an attachment recorded, or from exactly one remote naming a canonical repository on its server ([ADR 0011](decisions/0011-account-level-connections-and-local-setup.md)). It tries `--cwd`, then `CLAUDE_PROJECT_DIR`, then its working directory. Outside a checkout it still starts, and its tools explain how to clone or add the canonical remote; it writes nothing there.

`connect --server URL --client codex|claude|cursor` approves one connection for the tool and registers the bridge once in that tool's user-level settings through [runner/client-config.ts](../runner/client-config.ts): `claude mcp add --scope user`, `~/.codex/config.toml` (or `$CODEX_HOME`), or `~/.cursor/mcp.json` with `--cwd ${workspaceFolder}`. Other settings are preserved and no repository file is written. Participation guidance travels as the bridge's MCP server instructions. This is a convenience. Any MCP-capable tool can connect without it, and instructions do not prove an agent uses the context.

## Command families

| Purpose | Commands | Scope / resource boundary |
| --- | --- | --- |
| Discover | `list_namespaces`, `list_repositories`, `get_repository` | `cruce:read`; recorded state only |
| Preview reconciliation locally | `preview_reconciliation` (bridge only) | `cruce:read`; explicit disposable local Git computation; no provider cost or fetch; requires the owner’s authorized local workspace |
| Inspect workspaces and concurrency | `get_workspace`, `list_active_workspaces`, `get_workspace_updates`, `get_reconciliation`, `inspect_overlap` | `cruce:read`; overlap is advisory; divergence uses available objects only |
| Inspect cached source and provenance | `get_git_access`, `get_source`, `get_history`, `get_diff`, `read_artifact`, `get_lineage` | `cruce:read`; source requires locally available objects; never fetches |
| Inspect retention and activity | `get_retention`, `get_activity` | `cruce:read`; recorded status and pageable history; no provider calls |
| Inspect retention in storage | `inspect_retention` | `cruce:read`; explicit `source.read` resource operation; fresh fork/ref proof |
| Inspect finished work | `get_archive` | `cruce:read`; archived bundles newest first, or the bundle containing `subjectId` (`null` when it is not archived) |
| Inspect or recover stored source explicitly | `inspect_source`, `recover_source` | Read grant / `cruce:read`; `source.read` resource policy and idempotency key |
| Workspace lifecycle | `start_workspace`, `detach_workspace`, `end_workspace` | `workspace:write`; owner only for existing workspaces |
| Execution reports | `heartbeat`, `report_change` | `workspace:write`; must name the attached execution |
| Attach or clean up a fork | `attach_workspace`, `cleanup_workspace` | `workspace:write`; Artifacts resource operations |
| Retain revisions or evidence | `publish_revision`, `publish_artifact` | `revision:publish` / `artifact:publish`; Artifacts resource operations |
| Propose and review | `create_proposal`, `review_proposal`, `record_verification` | `change:write`; agent evidence stays `reported` |
| Read review notes | `get_review_notes` | `cruce:read`; the note thread of a workspace's open change, including notes inherited from changes it superseded, each marked as awaiting the owner, awaiting the reviewer or resolved |
| Add or answer review notes | `add_review_note`, `reply_review_note` | `change:write`; a note names the open change's exact revision; a reply may cite a published revision of the same workspace; never resolves |
| Ask for a human decision | `request_promotion` | `promotion:request`; not an approval |

Hosted MCP and the local bridge also offer one prompt, `address_review_notes`: fixed instruction text the user can run from a tool that supports MCP prompts to have their agent read the notes on their change, fix what it agrees with, publish and propose the new revision, and reply on each note. Cruce stores no prompts and never sends one.

Hosted discovery filters tools by granted scope. Scope never replaces current membership, the connection's repository approval, workspace ownership or namespace resource policy. Human concern and review-note resolution, rejection, attestation and promotion are absent from the agent catalog. An agent review with outcome `approve` never satisfies human approval. Repository Archive, Restore and permanent Delete are also console-only namespace Owner decisions. Archived repositories remain readable but reject writes; deletion freezes work and old deleted IDs remain unavailable ([repository lifecycle](domain-model.md#repository-lifecycle)).

Every coordination read uses established identity, current Namespace authority and recorded repository/cache state. HTTP, MCP and terminal routing perform no login, metadata save, schema creation or Artifacts call for these reads, including after a restart. Explicit sign-in/authorization creates the identity and personal namespace; human canonical setup or setup retry initializes repository state. MCP discovery does not initialize anything. Authentication still verifies Access identity and may refresh its signing certificates.

`inspect_source` is explicit cloud work: choose files (a listing without content, or one path), history, diff or a stored artifact through `sourceView`. Files, history and evidence use native Artifacts APIs without populating Git objects. History is labelled `first-parent` and reports truncation after 30 commits; it is not complete merge ancestry. Diffs may recover bounded retained Git objects. `recover_source` restores a retained exact revision for cache-only ancestry/diffs/pack export. Both consume one shared namespace reservation per request and recheck current authority/policy on retries. Source responses are not saved in command receipts. Binary/oversized files include an unavailable reason; tree/call/response limits fail explicitly. See [source/cache limits](architecture.md#bounded-source-inspection-and-recovery).

`inspect_retention` is explicit `source.read` work: it checks fork identity and the bounded complete ref inventory, then records exact unretained refs and check time. It never deletes a fork or grants cleanup authority. Cleanup checks again before requesting deletion. `get_activity` returns up to 100 retained events in oldest-first order and a continuation `cursor`; the recent snapshot window is not history deletion. An ended workspace whose fork is gone leaves `get_repository` with its closed changes, publications, evidence and settled promotions. `get_archive` pages those bundles 20 at a time, and reads that name an archived ID or revision still see it. Capacity failures preserve records and refuse new work. See [coordination/transfer bounds](architecture.md#bounded-coordination-state-and-retention-recovery).

There is deliberately no tool to launch, pause, resume, message or schedule an agent. There is no acknowledgement protocol, no ref-claim store, and no `clone`/`fetch`/`push` replacement.

## Participation protocol

1. **Start or continue.** Start a workspace at an exact baseline. Through the bridge, work only in the returned directory. To continue an existing workspace, call `attach_workspace` with its `workspaceId`; the bridge creates or reuses its owned worktree and returns the directory. An attachment elsewhere must first be explicitly detached. A new session can also point the bridge at the existing worktree, or use `cruce resume --workspace ID`. Keep the returned workspace IDs and pass them on workspace tools when coordinating parallel work; a bridge tracks presence and reports for the workspaces it starts, attaches or uses locally.
2. **Stay oriented.** At the start and whenever scope changes, inspect active workspaces, overlap and `get_workspace_updates`. The bridge renews presence and reports changes every 30 s while it runs.
3. **Use Git.** Commit and push to the workspace fork with ordinary Git. `publish_revision` retains the exact pushed revision; it cannot upload uncommitted changes. Pass `workspaceId` to publish from that workspace's own checkout. An uncertain publication in one workspace does not block another workspace's operations.
4. **Propose an exact revision.** Create a proposal from the published revision, record evidence for that exact revision, and request human promotion when ready.
5. **Answer review notes.** When notes await the owner, read them with `get_review_notes`. Fix what you agree with in the workspace directory, verify, push, publish and propose the new revision, then `reply_review_note` on each note with `citedRevision`. Reply with your reasoning where you disagree or need the user's judgment. A reply never resolves a note; a human maintainer does in the console.
6. **Reconcile just before proposing.** When canonical moves, merge it into the workspace right before publishing and proposing, or earlier when the user asks. Updating at that point means a human reviews once, on the revision that would land; updating every workspace as soon as canonical moves only creates revisions that go stale at the next promotion. Within the user's authorized task scope, an agent handles routine reconciliation in the workspace attached to it: preserve working changes, fetch canonical, merge with Git, verify, push, publish and propose the reconciled revision with fresh evidence for fresh review. A workspace not attached to the agent is updated only when the user asks to continue it. This does not inherently require human intervention. Ask the user when unresolved conflicts, ambiguous intent or failing checks require their judgment. Divergence does not establish conflicts, and a clean merge does not establish correctness. Fetching or receiving an update is not reconciliation; human approval of the resulting exact revision remains required for promotion.
7. **Detach or end deliberately.** `detach_workspace` frees the workspace for another checkout. `end_workspace` completes it without promoting anything. Fork cleanup is a separate, retention-checked step.

These steps are cooperative guidance, not scheduling gates. Cruce cannot make an agent read context, cannot see unconnected participants, and never reconstructs an agent conversation. In repositories with human-enabled observation, push events trigger identity-checked ref inspection with bounded backfill. `get_reconciliation` exposes its health and published-ancestry relationships; it never fetches or writes. `get_repository` includes an `attention` projection: per current change or reconciliation-needing workspace, its owner, exact revision, structured blockers and the caller's eligible actions. For an agent these are at most owner work (`prepare_revision`, `reconcile_with_git`) on its own user's workspaces; approval, attestation and promotion stay with authenticated human maintainers. It is a reading aid, not an assignment or a queue. `get_workspace` additionally exposes the bounded last observed fork-ref inventory. Publication and acceptance remain separate.

## Live bridge coordination updates

The stdio bridge appends fresh **Current coordination** context to tool responses, including errors. A leading `Cruce:` sentence names the caller's owned workspaces behind canonical and open changes whose notes await the owner. Attached workspaces are addressed within the user's task before publication/proposal; unattached workspaces wait for explicit continuation. Source already contained in canonical is finished rather than behind.

Context includes exact canonical/workspace/change revisions, authorized actions, blockers, unavailable comparisons, continuation IDs, review-note counts and up to sixteen advisory overlaps with owners and report freshness. Totals/truncation stay visible. Identical detail becomes a one-line unchanged notice, but the actionable lead still appears; the tool's structured result is unchanged. Failed reads report unavailable state without replaying cached authority or changing a completed mutation's outcome.

| Delivery | Contract |
| --- | --- |
| `repository_coordination` | Full context at `cruce://coordination/<namespaceId>/<repositoryId>` with URI-encoded IDs. Local MCP clients may read/subscribe; while subscribed, authorized cache-only polling every 30 seconds sends `notifications/resources/updated` on changed state. No subscription polling otherwise |
| `cruce hint` | Same lead on the user's next prompt. `connect --client claude` installs a `UserPromptSubmit` hook beside existing hooks. One authorized read in a Cruce checkout; no output elsewhere. No local state writes or prompt blocking |
| `cruce watch --coordination` | Initial and changed-state JSON lines every 30 seconds for external hosts. No heartbeat/report, fetch, reconciliation or process launch. Failed reads emit unavailable state |

Client hosts own subscription support, context consumption and continuation. A live bridge does not prove an agent is working; a notification does not guarantee a model turn. Hosted MCP has no background subscriptions from this bridge feature. Installed clients need the updated package. See [setup](native-setup.md) and [verification](local-verification.md#current-evidence-at-a-glance).

## Explicit local Git merge preview

`preview_reconciliation` through the bridge, or `cruce preview --workspace ID`, checks committed local HEAD against the current accepted canonical revision read under current authority. Observed canonical divergence/deletion leaves the preview unavailable pending maintainer reconciliation. It requires a locally registered workspace owned by the caller with current write access. Hosted MCP neither lists nor dispatches this local operation. It is marked mutating because it creates disposable local objects, with no infrastructure action or provider cost.

The preview runs native `git merge-tree --write-tree` in an isolated temporary bare repository borrowing existing immutable local objects. It uses Git defaults with global/system configuration, replacement objects and hooks disabled; repository-specific merge drivers/configuration are not used. Results name both exact commits and return `clean`, `conflicts`, `unrelated` or `unavailable`, with conflict paths/types where Git supplies them. Working changes are excluded and disclosed. Git exit status determines conflicts even when there are no individual conflicting paths. No fetch, ref update, checkout/index modification, test run, evidence, approval or promotion occurs. Missing objects require an explicit ordinary Git fetch and another preview. Each subprocess has a 30-second timeout and an 8 MiB output limit; scratch objects are removed after the attempt.

A preview is local merge evidence for its exact commit pair, not proof of semantic compatibility. Apply any merge explicitly in the workspace, preserve working changes, verify externally and publish fresh source/evidence for review. Other agents’ uncommitted changes are visible only through advisory reports, not included in this preview. Recheck canonical if it moves.

## Failures and retries

Mutations require an idempotency key. Retry with the same key and the exact same request after an uncertain outcome; the bridge keeps pending operation state for this. `heartbeat` and `report_change` are latest-wins observations: only the latest key per workspace replays, and an older key runs as a new observation, so the bridge sends a fresh one each tick instead of journaling it. Mutations on archived records are refused, except a retry of the operation that finished the work. Changed input needs a new operation once the earlier outcome is known. Access is checked again on every retry, so a stored receipt cannot authorize a revoked connection.

An unknown authenticated identity returns 401 with a sign-in instruction; reading never registers it. A registered repository whose setup was interrupted can be inspected without persisting an empty state; its console offers human maintainers an explicit setup retry. Unavailable cached source requires explicit `inspect_source` / `recover_source`, publication or Git transport, never a coordination read that silently provisions or fetches. A `preparing` workspace can be re-attached after a failed first attachment. Attaching a workspace that is attached elsewhere fails until that execution is detached. A lost heartbeat leaves locks and the attachment intact. Cleanup can return `deleting`; the submitted operation resumes through a bounded DO alarm under its original reservation and current authority/policy. `get_retention` exposes its recorded phase, blockers and last inspection without provider calls. A blocked operation needs an authenticated retry with its original key/input from anyone who could start it now; `get_workspace` and `get_retention` show the recorded command to them, the bridge resumes it under that key and the console offers it ([ADR 0015](decisions/0015-resuming-a-recorded-fork-deletion.md)). Changed or expired OAuth approval stops automatic recovery. Expiry never starts deletion. Report these states honestly.

The [current limitations](architecture.md#current-limitations) distinguish implemented recovery from remaining hosted fault-case acceptance. [F3 evidence](local-verification.md#pure-coordination-read-verification-f3) records local read-purity verification.

## Extending the surface

A new tool must pass the [boundary test](product.md#the-boundary-test) and express a Cruce concept, not a Git, forge or agent-framework primitive. Add it once in the shared catalog, define its contract and pure decision, and implement any I/O in the runtime. Resource actions declare scope and cost and use the namespace gate. Reads stay free of mutation and provisioning. Add behavioral tests for authority, exact revisions, retries and ownership.
